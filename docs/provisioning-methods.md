# Provisioning Methods and Templates

## Method Status

| YAML method | Status | Generated behavior |
| --- | --- | --- |
| `ssh`, `api`, `https`, or omitted | `rendered_unverified` | Existing family-level native `.cfg` renderer. These values do not cause network access or device execution. |
| `auto-rsc` | `rendered_unverified` | Versioned RouterOS 7 `.auto.rsc` template for declared `RB750Gr3`, OS train `7.x`, template version `1`. |
| `cisco-ztp` | `blocked` | Rejected until a model/release profile compatible with the TLS-only requirement is evidenced. |
| `cisco-autoinstall` | `unsupported` | Rejected because model/release discovery and filename behavior are not verified. |
| `fortimanager-ztp` | `unsupported` | Rejected until model, FortiOS release, backend and exact DHCP values are established. |
| `fortideploy-cloud` | `unsupported` | Rejected until model/release, entitlement and enrollment requirements are established. |
| Other values | `unsupported` | Rejected; generation never silently falls back to another method. |

`ProvisioningMethod` is a named domain type. YAML/JSON values remain strings for
backward compatibility. The existing values `ssh`, `api`, `https`, and
`auto-rsc` are retained; they describe the input intent, not an instruction to
connect to equipment.

## Template Metadata

Templates are embedded from `internal/adapters/generation/templates/vendors/`.
Each `metadata.yaml` declares a stable ID, version, manufacturer, model or
explicit `*` family scope, OS family/version values, provisioning method,
feature list, variable list, required-variable list, validation status, and
source references. `template_file` selects a non-default file; otherwise the
declarative Cisco interface loader uses `interfaces.cfg.tmpl`.

The loader computes SHA-256 from the exact template bytes. The RouterOS native
manifest records that checksum, the input/output checksums, supported features,
and `validation_status: render-only`. The site manifest carries the same
provenance additively; Agent validation keeps older manifests compatible.
Compatibility checks are hard gates for method, manufacturer, family, exact
model or declared wildcard, OS version, template version, required variables,
and requested features. No score can override a mismatch.

For a new profile:

1. Add the template and strict metadata under the existing vendor tree.
2. Record an official source and exact model/version scope. Use `render-only`
   until syntax acceptance has been observed on an identified target.
3. Add a resolver/render test for positive and hard-incompatibility cases.
4. Verify deterministic bytes, template and output hashes, catalog publication,
   site-manifest metadata, Agent staging, and no partial publication on error.
5. Never include private keys, credentials, or certificates containing private
   key material in templates, artifacts, or manifests.

## State Semantics

`rendered_unverified` means a local artifact was produced. It does not mean
`syntax_validated`, `lab_validated`, `hardware_validated`, uploaded, executed,
or verified. An Agent report that an artifact was staged is delivery evidence,
not device-side evidence.

RouterOS `.auto.rsc` uploads automatically execute under the official
RouterOS behavior. Keep generation and transfer separate. The current template
uses stable `infraflow:` comments and `find`/conditional `set` updates for its
owned entries; this is template-level repeat-safety and has not been validated
against CHR or hardware. See [the RouterOS CHR runbook](lab/routeros-chr.md).

Cisco ZTP, Cisco AutoInstall, and Fortinet provisioning are not generated by
the current code. Their documented blockers and required evidence are in the
[vendor provisioning audit](vendor-provisioning-audit.md).
